## Blocking

- **B1. The judge marks every successful run of a recipe with `expects` as failed, so its third success retires and archives it (D-153, WAVE3 (d)).** `crates/harness/src/judge.rs:145-150` looks for `expects.text` in some window line's `result_summary`. BrowserOS `wait for=text` returns `matched (text)` and does not repeat the text. In the live runs t27-accept-3 (send) and t27-accept-5 (draft), lines 15-16 are `wait for=text value="Message sent"` / `value=<subject>` with summary `matched (text)`, and no line in either file holds the expects text. So send (`Message sent`), draft (`{subject}`) and lu.ma register (`You're In`) are judged `Failed: expects text not seen` on every successful run, and `record` retires and archives them at 3 (lifecycle.rs D-153 branch). The test cannot catch this: `verdict_rules` (`judge_tests.rs:371`) puts `"Message sent"` into a wait's summary, which BrowserOS never produces. Fix: give `BrowserLine` the args and count an ok `wait` with `args.for == "text"` and `args.value == expects` and a summary that starts with `matched` (B-1500: `matched:false` comes back ok:true), keeping the summary-contains check as a fallback. Add a test built from the real line shape above.
- **B2. A hand-written recipe becomes `ephemeral` on its first judged run, so the T-7 sweep archives it after 14 idle days (lifecycle rules, D-153 "existing lifecycle rules").** `record` → `row` → `new_row` (`crates/toolstore/src/lifecycle.rs:149-158`) chooses Saved vs Ephemeral from the `<name>.js` header only. A recipe has no `.js`, so the T-27 recipes (send, draft, inbox, ...) get `Ephemeral`; `judge_tests.rs:333` (`an_ok_window_records_ok`) asserts this. With B1 they never reach 3 clean runs, and `sweep` (now going through `tool_file`, lifecycle.rs:688) retires and archives an ephemeral recipe unused for 14 days (or past 10 site visits), then reflect commits the move. Hand-written `.js` tools without `@forged` start Saved. tools.save already registers its own recipes as ephemeral with `register_forged`, so `new_row` should give `Saved` when `<name>.recipe.yaml` exists. Fix that and the assertion, and add a test that an idle hand-written recipe survives `sweep`.

## Should fix

1. **The two recipe validators disagree, and D-1503 (on main, newer than D-150) is not applied.** `RECIPE_TOOLS` (`recipe.rs:41-52`) still allows `screenshot`, `pdf` and `download`. D-1503 leaves them out because "a download opened any URL with no check". `parse_recipe` also does not check navigate URLs: `https` only, host equal to the folder, a subdomain or a `_site.yaml` alias, no `{placeholder}` before the path, no backslash, `@`, `%` or port in the authority. It also has no per-tool arg-key allowlist and no act-kind allowlist, and it does not require a declared arg to be used. `scripts/recipes/check_recipes.py` enforces all of these. The tests save recipes navigating to `https://x.y/` under other folders (`tests_recipe.rs:178,188`). The effect is that `tools.save` can write and git-commit into `tools/` a recipe that `scripts/recipes/test_check_recipes.py::test_every_recipe_in_tools_passes` rejects. For example, `save_substitutes_declared_values` declares an unused `one` arg, and a declared value equal to the host makes the host a placeholder (`https://{site}/`, off-site navigation by argument, which D-1502 rules out). Either port the rules into `parse_recipe` or record a supreme decision that supersedes one side.
2. **The B-599 (1) `@vault(` refusal can be bypassed by splicing placeholders.** `bind_args` (`forge.rs:492-499`) checks each arg value alone. A template such as `{user}@{host}` with `host = "vault(pw)"` fills to `alice@vault(pw)`, and no single value contains `@vault(`. Check the filled strings instead: refuse when a filled string has more `vault_refs` than its template (`fill_str`, forge.rs:548-567). Related: `parse_recipe` accepts `@vault(` in an arg `default` (`recipe.rs:812-824` never runs `plain_string` on defaults), although D-150 allows it only in act text/value. Only tools.run catches that case at run time.
3. **Rule 2: `forge::clip` cuts before it scrubs.** `forge.rs:390-402` is applied to caller input in classify `what` (206-210, which scrubs after the clip), `folder_of` (236), `run` (312), `bind_args` (461) and forge_save (311, 318, 327, 376, 404). A cut prefix of a long vault value (a token) is no longer the value, so core's whole-value scrub misses it. `ledger::clip` (`crates/core/src/ledger.rs:559-572`) scrubs first for exactly this reason. Do the same, with the harness vault.
4. **`regex_escape` may break BrowserOS grep patterns.** `forge.rs:533` escapes `# & - ~`. In an ECMAScript regex with the `u` or `v` flag, `\&`, `\#`, `\~` and `\-` outside a class are syntax errors. Check how BrowserOS compiles `grep` patterns, or escape only `^$\.*+?()[]{}|/`. `forge_save::with_form` must use the same set.
5. **Rule 7 gaps.** (a) `parse_recipe` and `tools.save` accept a literal em dash, en dash or ` -- ` in a recipe's own act `text`, `value` or `fields[].value`, so a saved draft or send recipe can carry one. (b) `bind_args` (`forge.rs:500-501`) matches only ` -- ` with spaces on both sides. It misses the mail signature separator `\n-- \n`, ` --\n`, and `--` at the start or end of the text. Treat `--` bounded by whitespace or a string edge as the separator.
6. **The judge can count a failure twice.** `judge_one` records the verdict (`judge.rs:360-370`) before `write_mark` (`judge.rs:296`). If the mark write fails, reflect returns an error and the next pass records the same run again, and that failure counts toward the 3. Write the mark first, or skip `record` when the mark write fails.
7. **The decisions do not match the code.** D-150 still says `description` 1..=200 and lists `screenshot, pdf, download`, and `Target.nth` is `Option<u32>` there. Amend D-150, or add a decision for B-214 (300) and B-216 (`Nth`), so the parser rule has one written source.
