Findings (none blocks a row):

- **Hook ok flag.** browseros_ledger.py records `ok: true` for BrowserOS timeouts. In t27-accept-2, `wait` returned "timed out after 10000ms waiting for selector" and `grep` returned "no matches". BrowserOS does not set isError on these, so ok is true. tools.save and reflect cannot tell a failed wait from a passing one by the ok flag.
- **Missing failed calls.** t27-accept-2r2 has only 4 lines, but the child reported a `wait` and a `grep` that timed out. Those calls never reached the ledger, probably because PostToolUse does not fire for a failed MCP call and the hook has no PostToolUseFailure entry. As a result, the ledger misses exactly the calls that fail.
- **Secrets in the inbox.** The inbox recipe hands mail snippets to the model unfiltered. On this run, row 4 of the inbox was a bank OTP mail with the code in the snippet. The child redacted it in its own report. It is not in any ledger line, because result_summary is cut at 300 chars and the code sat past that cut. A longer inbox or a different row order would put a one-time code in browseros.jsonl.
- **Weak thread wait.** As noted in row 4, `[role=main] h2` also matches on the search results page.
- **Events pattern.** The events grep only matches rows whose name starts with a weekday. If the Schedule view puts the day only on the first item of a day, later same-day items are missed. This run had one item per day, so it could not show either way.
- **Stray commits from my first child session.** I launched it with `--allowedTools` only, which pre-approves tools but does not restrict them. The Stop hook asked it for a handoff, and it committed 0a9f149 and 21f8c44. Those add agent-memory/handoffs/T-27-acceptance-inbox-1.yaml and a `next:` line on T-27 in agent-memory/tasks.yaml. Both describe the pre-4a2888f failure, which is now stale. I left them in place for the sub-orchestrator to revert or keep. Every later child ran with `--tools ""` and changed no files (git status clean after each).
